A CSRF token is a unique, secret, random unpredictable value generated by the server side application and shared with the client when performing sensitive actions, requests are only validated if they contain the CSRF token, and their is no way for the attacker to find out a CSRF token due to the SOP.

A way of sharing CSRF tokens might be using a hidden parameter in a html form
```
<form name="change-email" action="my-acc/change-email" method="POST">
	<label>Email</label>
	<input required type="email" name="email" value="example@normal-website.com">
	<input required type="hidden" name="csrf" value="50FaWgdOhi9M9wyna8taR1k3ODOR8d6u">
	<button class='button' type='submit'> Update email </button>
</form>
```
Some applications also place CSRF tokens in HTTP headers.
### Common Flaws in CSRF token validation

__Validation of CSRF token depends on request method__
In the situation in which the application only checks the validity of the `csrf` token only if the request method is say `POST`, one can just modify by the request method and bypass the `csrf` check, instead using a `GET` method.
```
<form action="https://0a94003c03f4ae5580bd17db00ad0003.web-security-academy.net/my-account/change-email" method="GET">
    <input type="hidden" name="email" value="anything@web-security-academy.net">
</form>
<script>
    document.forms[0].submit();
</script>
```

__Validation of CSRF token depends on token being present__
Some applications only verify the CSRF token if it is present, in that case simply omitting the token from the request results in the applications skipping the check and the CSRF attacks runs sucessfully.

__CSRF token is not tied to the user session__
Some applications do not validate that the token belongs to the particular user's session, rather they have a pool of `csrf` tokens, and if the token in the request matches any one of these tokens the request is trusted, thus a attacker could login to his account and use his token to perform a attack on another user.

Note that in most cases  `csrf` tokens are single use, so make sure to drop the request you make to update your email and use the csrf token from that request.

__CSRF token is tied to a non-session cookie__
Some applications do tie `csrf` tokens to a cookie but not necessarily to a session cookie, they might use something like a `csrfKey` cookie, and it might be highly possible that the system which checks this cookie is not integrated with the session management system, in this case if their is some way in which the attacker can set a cookie on the user side. Then a attack is possible. The attacker sets the `csrfKey` cookie on the user side and sends his own `csrf` token which matches with the key, this pair can be found using a new account which the attacker creates, a way to do this maybe if the response headers contain a `Set-Cookie` header which contains user controlled data such as a search term.

One can then use a form to store the email and the `csrf` token, which may be auto submitted as follows using a `img` tag which also sets the `csrfKey` cookie
```
<img src="https://YOUR-LAB-ID.web-security-academy.net/?search=test%0d%0aSet-Cookie:%20csrfKey=YOUR-KEY%3b%20SameSite=None" onerror="document.forms[0].submit()">
```

__CSRF Token Is simply duplicated in the Cookie__
In Certain applications csrf tokens are duplicated as a cookie and the applications only checks whether these two are equal for verification purposes. Thus if a application has cookie setting vulnerabilities as above then one can set the csrf cookie to anything and then supply a valid csrf token which allows attacks to proceed without any issue. The setup is similar to the case above.
